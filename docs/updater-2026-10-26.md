## Reproduction and root cause

Archived the exact failed-run main data with `git archive`, then called `run`
in preview mode using the existing credential helper. The complete Actions log
contains no traceback: the CLI deliberately suppresses exceptions. A local
DataValidationError-only traceback established this call path:

`nearLiveUpdater.run` → `update_league_data` → `prepare_league_update` →
`merge_incremental_rows` → DataValidationError (original dataUpdateSafety.py:259).

The daily replacement had already succeeded in staging. It was not the failing
schema check. The first completed matchup of 2027 caused the league updater to
construct a season without an existing same-season prefix. Its `if df.empty`
branch replaced the initialized frame with the first home-team frame, whose
assignment order placed Win/Loss before Home/Away. Appending to an existing
season normally inherits the prefix's canonical order and masks this defect.
The comparison checks whole frame column order before appending any records;
it does not compare only changed fields.

Persisted columns:

```
Year, Week, Type, Team Name, Team Abbreviation, Team ID, Team Owner,
Home/Away, Points For, Points Against, Win, Loss, Opponent Team Name,
Opponent Team ID, Opponent Owner, Cumulative Points For,
Cumulative Points Against, Cumulative Wins, Cumulative Losses, Weekly Rank, Rank
```

Incoming columns:

```
Year, Week, Type, Team Name, Team Abbreviation, Team ID, Team Owner,
Win, Loss, Home/Away, Points For, Points Against, Opponent Team Name,
Opponent Team ID, Opponent Owner, Cumulative Points For,
Cumulative Points Against, Cumulative Wins, Cumulative Losses, Weekly Rank, Rank
```

Missing: `[]`. Unexpected: `[]`. Zero-based order differences:

| Index | Persisted | Incoming |
|---|---|---|
| 7 | Home/Away | Win |
| 8 | Points For | Loss |
| 9 | Points Against | Home/Away |
| 10 | Win | Points For |
| 11 | Loss | Points Against |

Dtypes match except Opponent Team ID: historical float64 (null bye opponents)
versus incoming int64 (all actual opponents). That difference is legitimate and
is not the ordered-column check's failure. Daily schemas match exactly, including
optional null eligibility and historical unknown 3PA. No column naming change,
new field, or pandas/CSV schema migration occurred.

## Fix and validation

Weekly producers now verify exact field membership/uniqueness before explicitly
ordering generated fields to the persisted schema. Both standings and player
producers get this protection; missing/extra fields still fail. Persistence
still rejects order differences. No dtype coercion, migration, history rebuild,
or authorized-window expansion was introduced. Errors report source, full
schemas, missing/extra/duplicate fields, order differences, and safe stack
locations without dumping request exceptions.

Disposable complete live update added 10 league rows, 137 weekly player rows,
retained 8 daily corrections, added 1 activity row, and rebuilt metadata/calendar
snapshots. A second live execution returned `UPDATED []` and zero changes in
all four canonical datasets. Immutable rows were compared field by field:
930 league, 12,258 weekly players, 39,832 daily players, and 2,186 activity rows
from prior seasons were unchanged; daily rows outside authorized 2027 periods
1–7 were unchanged. CSV column order remained canonical in every dataset.

All frontend exporters generated successfully from this disposable data. Testing
also exposed an existing exporter test's assumption that team 16 must already
have departed players in the newest season. It now checks exact current and
former membership against the current roster snapshot when available, retaining
historical assertions otherwise. Production exporter behavior is unchanged.

Local results: 106 backend tests passed; 99 exporter tests passed against regenerated
outputs and the updated disposable canonical source; all 9 frontend test files
passed; Vite built successfully with the regenerated exports. Local runtime was
Python 3.12.14/Node 24.19.0 with the repository's pinned pandas/numpy/ESPN versions;
GitHub Actions provides the final Python 3.11/Node 22 production verification.
